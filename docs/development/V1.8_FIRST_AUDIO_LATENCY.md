# V1.8 首响延迟优化（2026-09-18）

## 依据和边界

- 原始收口代码 `71ee5f7`，对应 main squash `d57f5ba`。
- 本地已有 11 轮指标中，ASR final（VAD 结束后）p50 为 2391 ms，LLM 首 token p50 为 1282 ms，TTS 首块 p50 为 610 ms。各阶段中位数不能直接相加当作总耗时。
- 原有 `time_to_playback_ms` 从 turn 创建开始，包含等待用户、说话、VAD 静音确认，不能当作说完话后的纯响应时间。
- 代码会在检测到端点或录音上限的同一帧先调度 partial，再等待它结束并执行 final。这会在触发时额外增加一次 ASR 解码。
- 修复将两种端点检查移到 partial 调度之前。已在执行的 partial 仍安全等待；final 仍独立识别完整音频，且只发送一次。
- 没有更换模型、减少识别精度、改变 VAD 静音阈值或修改用户环境。

## PowerShell 复测

### 第三轮：减少静音期 ASR 竞争与音频复制

- 第二轮用户实测 endpoint-to-playback p50 为 3601.5 ms，LLM 首 token p50 为 633 ms，ASR final p50 为 1680 ms。仅四轮样本，不能据此承诺稳定 p95；长尾原因尚未确认。
- 原实现会在静音确认期继续启动 partial，与即将到来的 final 串行竞争；并且每帧先拼接完整 PCM 检查非空，即使 worker 正忙或未达到提交间隔。
- 新增 O(1) `partial_ready` 状态：只在 VAD 已开始、当前非静音且未结束时提交 partial；暂停后继续说话会恢复调度。将实际 PCM 拼接延后到确定提交后，每次提交只复制一次。
- 不改变录音内容、VAD 阈值、final 完整解码、单 worker 约束或已有任务安全等待。低能量语音被 VAD 判为静音时可能减少 partial 显示，但 final 仍包含所有已采集音频。
- 三项新增回归修复前失败；修复后完整 379 项通过，compileall/pip check/diff check 通过。复测方法沿用下文，额外测试句中短暂停顿再继续说话，确认 final 无截断且 partial 能恢复。
- 此次没有真实设备提速数值；首轮长尾仍待定位，没有擅自预加载模型或改动系统环境。

重点报告：

- `endpoint_to_playback_ms`：VAD 确认结束到播放启动，不包含此前的 VAD 静音确认；仍是软件事件计时，不是声卡实际出声测量。
- `endpoint_to_first_audio_ms`：VAD 确认结束到音频就绪。
- `asr_final_ms`：端点后的识别等待与 final 解码。
- `post_asr_setup_ms`：final 识别后到请求 LLM（含 SER、情绪状态、memory 等准备）。
- `llm_first_token_ms`、`first_sentence_ms`、`tts_first_chunk_ms`：后续各阶段。
